# Paired GM8 userspace-LMK startup candidate

Experimental `lineage-19.1-lmkd-test`, based on the 1.5 GiB zRAM/PPR-off
candidate 84fc751087f7e4777eb6cf380ec8f55bdfaeb429.

For SoC 313, if /sys/module/lowmemorykiller is absent, the actual post-boot
memory setup now takes an early userspace-LMK path. It explicitly disables
PPR if that node exists, retains allocstall_threshold=0 and swappiness=100,
then calls the existing zRAM, readahead and swap setup in their original
order. It never reads or writes missing KLMK/ALMK nodes in that path.

The preceding script remains usable with the old GM8 kernel: when the LMK
directory exists, original threshold and adaptive-LMK setup still runs, with
the already-established PPR-off policy for 313. Other SoC paths retain their
preceding behavior. This fallback is not permission to mix release artifacts:
the matching device candidate requires a memcg-enabled, KLMK-disabled kernel.

This supersedes the retained PPR-test document's statement that KLMK stays
active, only for the paired new-kernel candidate. zRAM remains 1610612736
bytes for the captured 3 GiB non-Go GM8. Compression and CPU/thermal policy
are unchanged by this commit.

Host tests execute the actual shell memory function against temporary files
for six new-path combinations (PPR missing/0/1, both SoC-ID paths), with no
legacy LMK directory. They require zero stderr, PPR off and original normal
setup calls. The preceding tests also pass for old-kernel GM8, other SoCs,
actual zRAM selection and substituted mkswap/swapon ordering:

```sh
python3 tools/tests/lmkd_policy_19_1_test.py --vendor .
```

The complete Android mksh script has not been run on a phone here. A full
Android build and hardware validation remain required. Install the complete
paired ROM, not just boot.img; the new startup behavior lives in vendor.
