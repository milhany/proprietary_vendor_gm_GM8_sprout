# GM8 Android 12 process-reclaim and zRAM experiment

The October 27 device capture has severe app-switch stalls, high swap traffic,
a low-memory event and application SIGKILL exits. It does not identify every
kill's source, nor establish a memory leak. The Instagram warmer-service test
did not improve usability. A smaller cached-process budget was withdrawn
because the owner already experiences frequent application reloads.

## Vendor memory changes

The shipped `init.qcom.post_boot.sh` runs configure_memory_parameters for the
msm8937 platform with SoC ID 313 (the GM8 MSM8940 board). Its non-premium path
enables the Qualcomm per-process reclaim worker, with a vmpressure window of
50-70, swap_opt_eff 30 and per_swap_size 512 pages. It derives min_score_adj
from the legacy LMK adj series. The pinned GM8 3.18 `mm/process_reclaim.c`
registers a vmpressure notifier and schedules a worker that selects eligible
processes by anonymous size, then calls reclaim_task_anon.

The experimental 313 branch explicitly writes 0 to enable_process_reclaim and
skips those extra-worker tuning writes. Normal kernel VM reclaim, LMK
thresholds/adaptive LMK, application cache budget,
ART heaps and install/background compilation policy retain their existing
behavior. This reduces one source of proactive reclaim activity; it does not
disable swapping or guarantee lower RAM use. Normal VM reclaim can still swap
pages, and changes in reclaim timing can also affect kills/reloads.

At the owner's request the next candidate also increases logical zRAM from
1 GiB to **1.5 GiB (1610612736 bytes)** for msm8937/SoC 313 non-Go devices
reporting more than 2 GiB and at most 3 GiB MemTotal. The captured GM8 value
2,891,416 KiB matches this gate. Smaller/larger memory variants, other SoCs and
Go compression behavior retain their preceding settings. Capacity is selected
before mkswap/swapon at boot; no running swap device is resized.

Logical capacity is not a reservation of 1.5 GiB physical RAM: compressed data
and metadata consume memory as the device is used. Extra capacity can retain
more anonymous pages but can also increase physical pressure and compression
work. It does not increase physical RAM or guarantee faster app launches.
This combined PPR/zRAM candidate must be assessed for stalls and reloads; an
improvement alone cannot attribute the benefit to just one of the two changes.

This is a controlled performance candidate, not proof that PPR caused the
freezes. Actual PPR state on the installed phone and a before/after comparison
remain required. Full Android build, signing and hardware validation have not
been performed here. No particular launch-time or RAM-footprint result is
claimed, and stock Pie's displayed average is not a controlled baseline for
Android 12 with different processes/app versions.

## Immediate device comparison, if root is already available

Read the actual state first:

```bat
adb shell su -c "cat /sys/module/process_reclaim/parameters/enable_process_reclaim"
```

If it reports 1, temporarily disable only that worker:

```bat
adb shell su -c "echo 0 > /sys/module/process_reclaim/parameters/enable_process_reclaim; cat /sys/module/process_reclaim/parameters/enable_process_reclaim"
```

Expected readback is 0. If it was already 0, PPR was inactive and disabling it
does not explain a performance change. If `su` is missing or access is denied,
do not alter security policy or install root just for this test. A vendor
update can apply the same setting during boot instead. On the old ROM the
original startup script normally re-enables PPR after reboot; an initial value
of 1 can also be restored with the same command writing 1.

Restore the Instagram component from the previous unsuccessful experiment and
compare normal app switching without removing tasks, forcing compilation,
changing cache limits or resetting app data. Check stalls *and* reloads. A
bugreport can be collected without waiting for a complete freeze; historical
kernel records may still help distinguish LMK/OOM and reclaim stalls.

## Persistent build

This source change is applied at vendor startup on every boot of the
experimental ROM. Building only boot.img cannot install a vendor shell script.
Build updated user target-files with the current device/kernel and this vendor
revision, then sign with the existing GM8 release keys before generating and
installing an OTA. No clean build or Format Data is required solely for this
script change. Keep the working release package available for rollback.

## Host validation

The test executes the actual original and modified configure_memory_parameters
function using temporary sysfs/proc substitutes. It reproduces original 313
PPR enablement, checks that the candidate disables an initially enabled worker,
retains LMK adj/minfree arrays, adaptive LMK configuration, swappiness and normal
zRAM/swap setup calls, and leaves 294/321 SoC behavior unchanged. The modified
function is executed by bash; the complete Android mksh startup script is not
claimed to have been executed on the host.

The actual zRAM sizing function is also executed against temporary files with
device commands substituted. It selects 1.5 GiB for the captured GM8 memory
size, keeps the stock choices for seven other RAM/SoC/platform/Go cases, and
retains the compression selection and swap-device command sequence.

```sh
python3 tools/tests/ppr_policy_19_1_test.py --vendor .
```

shallow checkout that lacks that commit. Relevant kernel source is
milhany/android_kernel_gm_msm8937 at
44e09019575c012ad5b332250261d162ea5835d5, mm/process_reclaim.c and
drivers/staging/android/lowmemorykiller.c. No raw device log is included.
